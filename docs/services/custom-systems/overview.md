# نظرة عامة على Individuelle Software

## الوعد الذي نستطيع تنفيذه

> أفهم العملية التي يريد العميل تحسينها، وأبني أصغر تطبيق ويب عملي يخدمها بوضوح، مع واجهة وBackend وقاعدة بيانات ونشر مناسبين للنطاق المتفق عليه.

لا نعد العميل بأن النظام سيحقق مبيعات أو يوفر مبلغاً محدداً أو ينجح تجارياً. نضمن وضوح العملية والنطاق وجودة التنفيذ التقنية المتفق عليها.

## لمن تناسب الخدمة؟

- شركة تعتمد على ملفات ورسائل وخطوات يدوية تريد تنظيمها.
- نشاط يحتاج حجوزات أو بوابة عملاء أو لوحة داخلية خاصة به.
- مؤسس يريد اختبار SaaS أو Subscription application بنسخة أولى حقيقية.
- شركة لا يناسبها برنامج جاهز، أو تحتاج ربط فجوة واضحة بين أدواتها.
- مشروع يحتاج بيانات وصلاحيات وعمليات تتجاوز الموقع التعريفي.

## الوظائف ليست باقات

هذه أمثلة على Modules يمكن أن تدخل في المشروع، وليست خدمات يجب جمعها كلها:

- Authentication وOAuth.
- Roles وPermissions.
- Admin dashboard.
- Payments أو Subscriptions.
- Email وNotifications.
- Uploads وStorage.
- Search وFilters.
- CMS أو Blog workflow.
- PostHog أو Product Analytics.
- Reports وExports.
- APIs وWebhooks.

يُختار ما يخدم النسخة الأولى فقط. لا نضيف Analytics أو Automation أو AI لأن أسماءها جذابة إذا لم تكن لها حاجة واضحة.

## قاعدة 80/20

لا نبيع النظام الكامل من أول مرة. نحدد العملية الأساسية التي تحقق معظم القيمة، ثم نبنيها ونختبر استخدامها قبل إضافة الحالات النادرة والأتمتة الواسعة والتقارير المتقدمة.

مثال Booking:

- النسخة الأولى قد تشمل خدمة واحدة أو فريقاً صغيراً وطلب موعد وحالة واضحة وإدارة بسيطة.
- الفروع والموظفون والدفع وسياسات الإلغاء والتذكير والتقارير تُضاف فقط إذا كانت ضرورية أو في مراحل لاحقة.

## حدود القدرة والصدق

تعكس الخدمة قدرة مطور Full-Stack مستقل على بناء Web applications عملية. لا تُسوّق حالياً على أنها:

- Enterprise engineering غير محدود.
- تطبيقات Native للهاتف دون تقييم منفصل.
- أنظمة طبية أو مالية أو شديدة الحساسية دون خبرة أو مراجعة متخصصة.
- SLA أو توافر دائم على مدار الساعة.
- بديل كامل عن فريق كبير عندما يحتاج المشروع عدة تخصصات متزامنة.

عندما يتجاوز العمل القدرة الحالية، يمكن تقليل النطاق أو تقسيمه أو التعاون مع متخصص أو رفضه.
