# تصنيف المشروع

## الهدف

لا نسمّي كل طلب برمجي Custom System، ولا نضع نظاماً حقيقياً داخل Add-on رخيص. يعتمد التصنيف على البيانات والمستخدمين وسير العمل والمخاطر، لا على عدد الشاشات وحده.

## Website أو CMS

يبقى الطلب ضمن المواقع عندما يكون هدفه الأساسي عرض محتوى عام، مثل:

- صفحات تعريفية.
- Blog بملفات داخل المشروع.
- CMS جاهز ومدير واحد ونطاق تحرير محدود.
- نموذج تواصل قياسي.
- رابط أو Embed لخدمة حجز خارجية.

## Shopify Onlineshop

يبقى المشروع ضمن خدمة Shopify عندما يكون جوهره بيع المنتجات من خلال Shopify، حتى إذا احتاج:

- عدداً كبيراً من المنتجات أو Collections.
- Theme مخصصاً أو Custom Sections.
- واجهة Storefront منفصلة أو Headless CMS للمحتوى.
- تطبيقات جاهزة أو Integration محدوداً يمكن عزله واختباره.

عدد المنتجات أو استخدام Headless لا يحوّل المتجر وحده إلى نظام عمل مخصص. ينتقل المشروع إلى Individuelle Software عندما يصبح المطلوب Workflow مستقلاً، أو Portal وصلاحيات وبيانات خاصة، أو Integration حرجاً يشغل عملية الشركة خارج دورة Shopify القياسية.

## Add-on أو عمل تطوير محدود

يكون الطلب محدوداً عندما:

- يضيف وظيفة واحدة واضحة إلى مشروع نعرفه.
- لا ينشئ نظام بيانات وعمليات مستقلاً.
- يمكن فحص أثره واختباره والرجوع عنه بأمان.
- لا يحمل المطور مسؤولية نظام خارجي كامل.

قد يدخل هنا إعداد PostHog داخل مشروع نبنيه، Webhook بسيط، Export محدود أو Automation واحدة.

## Custom MVP

ينتقل الطلب إلى تطبيق مخصص عندما يحتوي عادةً على عدة عناصر من الآتي:

- Accounts أو Authentication.
- Roles وPermissions.
- بيانات عمل دائمة ومترابطة.
- حالات تتغير ضمن Workflow.
- Admin dashboard.
- Payments أو Subscriptions.
- Notifications أو Scheduled jobs.
- Integrations تؤثر في سير العمل.
- اعتماد الشركة عليه في عملية يومية.

النسخة الأولى تركز على Workflow رئيسي واحد وعدد محدود من الأدوار والتكاملات.

## Business System

يصبح Business System عندما يجمع أكثر من عملية مترابطة أو عندما يعتمد عليه عدة أنواع من المستخدمين، مثل:

- موظفين ومديرين وعملاء.
- حجوزات مع خدمات وموظفين وفروع وسياسات.
- إدارة طلبات ومدفوعات ومخزون وتقارير.
- Customer portal مع عمليات داخلية ولوحة إدارة.
- تكاملات متعددة أو استيراد وتصدير بيانات مهم.

هذا المستوى يحتاج Discovery ومراحل، ولا يحصل على سعر فوري في أول مكالمة.

## Advanced Custom System

علاماته تشمل:

- Multi-tenancy أو SaaS كامل.
- Billing مع خطط وفواتير وحالات دفع متعددة.
- صلاحيات دقيقة وAudit logs.
- معالجة خلفية أو Real-time.
- حجم بيانات أو توافر أو أمان مرتفع.
- متطلبات قانونية أو تنظيمية خاصة.
- عدة Integrations حرجة.

Advanced هو تصنيف داخلي للمخاطر وليس بطاقة سعر مستقلة. يُقسّم إلى مراحل أو يُنفذ مع متخصصين أو يُرفض.

## قاعدة سريعة

إذا اجتمعت ثلاث إشارات من الحسابات والصلاحيات والبيانات والعمليات والإدارة والتكاملات، أو ظهرت إشارة عالية المخاطر مثل الدفع أو البيانات الحساسة، فلا يُعطى سعر Add-on قبل تقييمه كنظام.

## حدود الأنظمة الخارجية

هناك فرق بين:

- استخدام API موثق لخدمة خارجية مثل Stripe أو PostHog داخل نظام نبنيه ونختبره.
- الدخول إلى Codebase أو نظام عميل بناه طرف آخر وتغييره مباشرة.

لا يُقبل النوع الثاني تلقائياً. يُرفض عندما تكون التقنية غير مألوفة، أو لا توجد Staging وTests وBackups وصلاحيات مناسبة، أو لا يمكن معرفة أثر التعديل والرجوع عنه. ليس على المطور أن يخاطر بتعطيل نظام لا يملكه ولا يفهمه بالكامل من أجل قبول عمل صغير.
